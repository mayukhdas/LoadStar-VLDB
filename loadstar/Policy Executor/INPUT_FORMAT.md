# LoadStar Policy Simulator

## Usage Instructions

To run the simulation:

1. Prepare your `testbed_filename` CSV file with testbed replica trace data
2. Prepare forecast files for load, CPU, memory and storage (generated by LUNA forecasting scripts)
3. Create an `input.txt` configuration file for the simulation setup
4. Cmpile and Run the simulator from command line:

```bash
g++ main.cpp -o policy_executor

./policy_executor <testbed_filename> 10 <load_forecast_file> <cpu_forecast_file> <memory_forecast_file> <storage_forecast_file> <input.txt> <output.txt>
```

**Parameters:**
- `<testbed_filename>`: Input CSV file with CosmosDB replica trace data for testbed (omi .csv extension), e.g., from [Zenodo repo](https://doi.org/10.5281/zenodo.15564578)
- `<load_forecast_file>`: Forecast file with load predictions from LUNA
- `<cpu_forecast_file>`: Forecast file with CPU predictions from LUNA
- `<memory_forecast_file>`: Forecast file with memory predictions from LUNA
- `<storage_forecast_file>`: Forecast file with storage predictions from LUNA
- `<input.txt>`: This configuration file
- `<output.txt>`: Output log file

**Note:** Ensure all forecast files are in the same directory as the main executable.


## Testbed Data Format (`testbed_filename`)

The input CSV file referenced during execution should contain replica data in the following format:
```
timestamp,UniqueReplicaId,PartitionId,ReplicaId,Load,CPU,Memory,Storage
```

Example:
- timestamp: Time period (integer)
- UniqueReplicaId: Unique identifier for the replica
- PartitionId: Partition identifier
- ReplicaId: Replica number
- Load: Current load on the replica
- CPU: CPU usage
- Memory: Memory usage
- Storage: Storage usage



## Input Configuration File Format (`input.txt`)

This details the format of the Input Configuration File (`input.txt`) used by the LoadStar policy simulator. The input configuration file contains system parameters and simulation settings, one value per line. These parameters define the cluster configuration, resource thresholds, and simulation behavior.

### Parameter Details

The following values need to be provided, one per line:

1. **Skewness parameter** (float, e.g., 1.0)
   - Controls the distribution pattern of load across nodes
   - Valid range: typically 0.0 to 2.0+
   - Higher values indicate more skewed/uneven load distribution

2. **Load capacity of node** (integer, e.g., 5000000)
   - Maximum load capacity per node in the cluster
   - Unit: Load units (as defined in your input CSV data)
   - This is the soft load capacity threshold used for placement decisions

3. **Number of nodes** (integer, e.g., 10)
   - Total number of nodes in the cluster
   - Valid range: positive integer (1 or more)
   - Defines the size of your cluster

4. **Hard load capacity of node** (integer, e.g., 5000000)
   - Absolute maximum load capacity per node (hard limit)
   - Unit: Load units
   - Once a node reaches this capacity, no more replicas can be placed on it
   - Should be >= Load capacity of node

5. **CPU threshold** (integer, e.g., 6000000)
   - Maximum CPU utilization allowed per node
   - Unit: CPU units (as extracted from input CSV data)
   - Exceeding this triggers migration decisions by the policy
   - Used in forecasting to predict potential overloads

6. **Memory threshold** (integer, e.g., 3)
   - Maximum memory utilization allowed per node
   - Unit: Memory units (as extracted from input CSV data)
   - Exceeding this triggers migration decisions by the policy
   - Used in forecasting to predict potential overloads

7. **Storage threshold** (integer, e.g., 2000)
   - Maximum storage utilization allowed per node
   - Unit: Storage units (as extracted from input CSV data)
   - Exceeding this triggers migration decisions by the policy
   - Used in forecasting to predict potential overloads

8. **Use soft load capacity?** (Y/N)
   - Whether to enforce soft load capacity constraints
   - Y: Enable soft load capacity limits (recommended)
   - N: Disable soft load capacity limits, only hard limits apply

9. **Soft load capacity** (integer, if Y above, e.g., 4500000)
   - Target load capacity per node (softer threshold than hard capacity)
   - Unit: Load units
   - Used by policies to make proactive placement decisions before reaching hard limits
   - Should be <= Hard load capacity of node
   - Only required if "Use soft load capacity?" is Y

10. **Policy type** (integer, e.g., 9)
    - Placement and migration policy to use for the simulation
    - See Policy Types section below

11. **Forecast window size** (integer, e.g., 12)
    - Number of future timestamps to consider in forecasting
    - Valid range: positive integer (1 or more)
    - Example: 12 means the policy will predict resource usage for the next 12 time periods
    - Larger values provide more lookahead but may miss immediate overloads

### Policy Types

| Type | Name | Description |
|------|------|-------------|
| 9 | WorstFitWithCPUMemoryRUPrediction | **Recommended** - Uses combined CPU, memory, and load forecasts to predict overloads and place replicas proactively. This policy balances load across nodes while considering all resource dimensions. |

### Migration Strategies

The policy uses the selected migration strategy to choose which replicas to migrate when a node is overloaded:

| Type | Name | Description |
|------|------|-------------|
| 1 | Binary selection | Selects replicas using a binary search algorithm to find suitable candidates for migration |
| 2 | Lightest replica selection | Selects the replicas with the smallest resource footprint for migration (may require more migrations) |
| 3 | Heaviest replica selection | Selects the replicas with the largest resource footprint for migration (fewer migrations, larger impact) |

- Memory threshold: 3 units
- Storage threshold: 2,000 units

### Internal System Parameters

FYI, these input parameters map to the following internal system parameters within the simulator:

- **NODE_COUNT**: Number of nodes
- **NODE_LOAD**: Load capacity of node (soft threshold)
- **CPU_LOAD**: CPU threshold
- **MEMORY_LOAD**: Memory threshold
- **STORAGE_LOAD**: Storage threshold
- **FORECAST_WINDOW_SIZE**: Forecast window size



## Output Files

The simulation produces the following output files:

- **NodeState.csv**: Shows the state of each node at every timestamp, including resource utilization and replica placements
- **MigrationInfo.csv**: Records all replica migrations that occurred during the simulation

## Notes

- Soft and hard capacity thresholds work together: soft limits trigger early migrations, while hard limits prevent new placements
- The forecast window size significantly impacts policy effectiveness—larger windows provide better lookahead but require more computational resources
- All resource thresholds (CPU, Memory, Storage) should be realistic based on your actual node specifications
- The WorstFitWithCPUMemoryRUPrediction policy recommends replicas for migration based on combined resource utilization forecasts
